> **Installing an agent plugin runs untrusted code and content.** CAO does not
> verify plugin authorship or integrity — there is no signing and no provenance
> check, and this feature deliberately does not invent one. A plugin you install
> can contribute instructions that your agents will read and act on. **Only
> install agent plugins from sources you trust.**

CAO is a client for the [Agent Plugins](https://agent-plugins.org/specification)
standard (version 1.0.0). An *agent plugin* is a directory containing a
`plugin.json` manifest and, optionally, a `skills/` directory. Installing one
makes its skills available to every CAO-supported provider.

> **Not the same thing as event plugins.** CAO has a second, unrelated system
> also historically called "plugins": Python hooks that react to server-side
> events inside `cao-server`. Those are **event plugins** and they are documented
> in [Event Plugins](plugins.md). The two systems share no code, no directory,
> and no configuration. Throughout CAO's documentation, "agent plugin" and
> "event plugin" are always written in full; a bare "plugin" is only used inside
> a page whose title already scopes it.

## What CAO supports today

CAO implements the **skills-only** profile of the specification, which
[§11.2](https://agent-plugins.org/specification) establishes as a conformant
client. Concretely:

| Component | Supported | Notes |
|---|---|---|
| `plugin.json` manifest | Yes | Validated against a schema vendored in this repository; never fetched over the network ([§5.2](https://agent-plugins.org/specification)) |
| `skills/` | Yes | Each immediate child directory containing a `SKILL.md` becomes a skill |
| `mcp.json` | **Not yet** | Detected and reported as unsupported; the plugin's skills still load |
| `extensions` namespaces | Ignored | CAO implements no extension namespace and does not validate namespace contents ([§8.1](https://agent-plugins.org/specification)) |

A plugin that ships an `mcp.json` is **not** rejected. CAO records that the file
is present, reports "MCP servers are not supported in this CAO version", and
delivers the plugin's skills unaffected — which is what
[§11.3](https://agent-plugins.org/specification) prescribes for an unsupported
component type.

## Prerequisites

These apply to CAO's **own** operator package (`agent-plugin/cao`), which ships
an MCP server so a foreign client can drive a CAO fleet. They do not apply to
plugins in general, and they do not apply to the contributor package.

| Prerequisite | Why |
|---|---|
| The `uv` toolchain on `PATH` | The packaged MCP server is launched via `uvx`. [§7.2.1](https://agent-plugins.org/specification) requires `command` to be a single executable token, so the package cannot bundle a launcher. |
| A CAO API server running locally at `http://127.0.0.1:9889` | Every operation the packaged MCP server exposes is an HTTP call to that server. Start it with `cao-server`. |

### Localhost-only posture

CAO's API server binds `127.0.0.1` by default and the packaged plugin never
reaches a remote endpoint. Nothing in either package opens a listening socket.

If you override `CAO_API_HOST` or `CAO_API_PORT` to a non-loopback address, you
have knowingly left that posture — CAO has not silently changed it for you.

## The two CAO packages

CAO publishes itself as **two** agent plugins, split by audience. Install the one
that matches what you are doing:

| Package | Install this if you want to… | Skills |
|---|---|---|
| [`agent-plugin/cao`](../agent-plugin/cao) | **Drive a CAO fleet** from another Agent-Plugins-compatible client: launch sessions, route work to the right agent profile, message running agents | `cao-session-management`, `cao-agent-routing`, `cao-supervisor-protocols`, `cao-worker-protocols` |
| [`agent-plugin/cao-contributor`](../agent-plugin/cao-contributor) | **Extend CAO itself**: author a new provider, or author an event plugin | `cao-provider`, `cao-plugin` |

The split is not cosmetic. The operator package's job is "drive a fleet";
shipping repo-development skills inside it would enlarge the prompt surface of
every agent that installs it with instructions it will never act on.

Both packages are committed to this repository, so they can be installed from a
clone with no build step, or straight from a subdirectory of the GitHub repo.
They are regenerated by `make agent-plugin` and guarded against drift by `make
check-agent-plugin`, which also validates them against the pinned schemas on
every pull request.

## Installing a plugin

```bash
# From a local directory
cao plugin add ./path/to/plugin

# From a git repository, optionally at a ref and/or a subdirectory
cao plugin add https://github.com/owner/repo
cao plugin add https://github.com/owner/repo --ref v1.2.3
cao plugin add https://github.com/awslabs/cli-agent-orchestrator --subdir agent-plugin/cao

# Check a candidate without installing anything
cao plugin validate ./path/to/plugin

# See what is installed, and which skills each plugin contributes
cao plugin list
cao plugin list --json

# Remove one (warns first if a live session can reach its skills)
cao plugin remove <name>
cao plugin remove <name> --purge-data
```

`cao plugin add --dry-run` resolves and validates without installing, which is
the same code path `cao plugin validate` uses.

## Where things are stored

```text
~/.aws/cli-agent-orchestrator/
├── agent-plugins/
│   ├── <plugin-name>/               # the plugin's own bytes, never modified by CAO
│   └── .state/<plugin-name>.json    # CAO's install record
├── agent-plugin-data/<plugin-name>/ # persistent plugin data, survives updates
└── skills/                          # skills, including projected plugin skills
```

Both directories are created owner-only (`0700`).

`agent-plugin-data/` is deliberately a *sibling* of `agent-plugins/`, not a
child: updating a plugin replaces its package directory wholesale, and
[§9.1](https://agent-plugins.org/specification) requires persistent plugin data
to survive that. `cao plugin remove` keeps this data by default; `--purge-data`
deletes it.

## How plugin skills reach your agents

A valid plugin skill is **projected** into CAO's normal skill store as a managed
symlink, so every existing delivery path picks it up with no provider-specific
configuration. See [Plugin-provided skills](skills.md#plugin-provided-skills) in
the skills guide for the projection rules, including how name collisions are
resolved and the one case where plugin skills do not reach a provider.

## Containment

Every path CAO reads out of a plugin is resolved with `realpath` and must land
inside that plugin's own directory
([§4.1](https://agent-plugins.org/specification)). A symlink pointing *inside*
the plugin is fine; one pointing outside is rejected.

Rejection is scoped as narrowly as the specification allows, so one bad path
does not take down a whole plugin:

| What escapes the plugin root | What is rejected |
|---|---|
| `plugin.json` | the whole plugin |
| `skills/` | all skills, but other component types still load |
| one skill's `SKILL.md` | that one skill |

Containment is **not** a sandbox. It governs which files CAO will read from the
package; it does not restrict what a skill's instructions may persuade an agent
to do. That is why the warning at the top of this page matters.

## Troubleshooting

**A skill the plugin ships is not showing up.** Run `cao plugin list`. Every
skill that was discovered but not projected has a finding explaining why —
usually a name collision with an existing skill, or with another plugin.

**`cao plugin add` failed and printed findings.** Nothing was installed: CAO
validates the staged copy before publishing anything, so a failed install leaves
your existing plugins untouched. Each finding cites the specification clause it
enforces.

**A plugin reports "MCP servers are not supported in this CAO version".** Expected
— see [What CAO supports today](#what-cao-supports-today). Its skills still work.

**Symlinks are unavailable in my environment** (for example Windows without
Developer Mode). Set `skills.projection_mode` to `"copy"` in
`settings.json`; CAO also falls back to copying automatically and reports it.
